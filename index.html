05 · The Hub, home

One launcher, one inventory

The digest panel states, module by module, what is installed, what is ready, and what needs attention, in plain words. Below it, your own categories hold shortcuts to the external tools you already use: drag them into the order you work in.

  • No "site mode." There is no site picker standing in front of your tools: all work is siteless.
  • Nothing is saved automatically. Everything a module finds this session lives in the one session working set, where every module can use it; unsaved work is forgotten when the app closes.
  • Saving is Save to My Files & Library, and a site name is required. Nothing is filed without one. What you save lands in category folders under <site> / Exports / in the Library — and the Library is your real folders on this computer, not a database inside the app.
  • Device backups are asked-first. A backup starts by asking what it should include and files into the Library under Device Backups; declining the backup means no backup is made.
  • Evidence, not memory. The things you file (captures, reports, backups, session logs) collect against the device and the site, so the next visit starts from evidence.

06 · Programmer+

The PPCL workbench

A full workbench for PPCL (the Siemens panel programming language), rebuilt as a native module of the Hub. Programmer+ works on program files, it never communicates with a panel.

Editor: checks run as you type; every finding says what to do and why.
  • An editor that checks as you type. Syntax colouring and a findings panel driven by 97 named diagnostics and logic checks. Every finding says what to do, why it matters, and where the rule comes from, including cross-line logic checks that catch a start command cancelling itself within the same pass.
  • A builder that compiles to PPCL. Block diagrams (31 block types), sequences written as structured lines, and decision tables, all compiling to program text, with plain-language refusals when something can't compile instead of silent guesses.
  • Library, point database, and imports. A file-based code library with collections, tags, and provenance; the point database with unresolved-reference marks in the editor; and vendor imports that arrive with a fidelity report stating, per item, what mapped cleanly, what was approximated, and what didn't map at all.
  • Report on this…, straight to Reports+. The Editor hands over its current program (Report on this program…) or its whole session set as a findings subject; the Simulator hands over a bench run, a run comparison, or a debug session; the Library hands over a panel report, a conversion, or the library itself; the Builder hands over a sequence import; the module chrome hands over the loaded point database. Reports+ opens with the subject in place and its report preselected. If Reports+ is not installed, the action stays visible and says so.
  • Help inside the module. A searchable 22-topic help, including the block reference, offline, like everything else.

A simulator and debugger

Run a program against a plant before you ever touch a panel: live trend charts, run comparison overlays, and a time-scrub back through every recorded pass. The debugger offers breakpoints (including watchpoints that stop when a point is written) stepping, run-to-cursor, and coverage.

Plants can inject faults, and a free-run mode runs your logic against a bare point store whose inputs never move on their own, so the trace is evidence about the logic, and only the logic.

Simulator: a completed free-run — the trace is evidence about the logic, and the surface states what the program does not drive.
Programmer+ in full, the complete capability list

Language & checking

  • Full PPCL language core: lexer, error-tolerant parser (a bad line is flagged, never fatal to the file), and control/data-flow analysis across the whole program, including loop wrap-around.
  • 90 lint rules in five families (syntax, flow, semantics, style, performance) each with a fix guide; panel-report findings (R-codes) for the problems panels themselves report; and two cross-line logic checks of Programmer+'s own (labelled as such in the panel, they are not manual rules).
  • Findings are a triad, always: what to do, why it matters, and the source the rule comes from.
  • Formatter and transforms: DEFINE expand/collapse, separator swap, clone-range, enable/disable lines, comment tools, all reference-aware, so renumbering rewrites every GOTO, DEFINE, and point reference consistently.

Authoring

  • Program generator with five templates, plus engineering helpers.
  • Sequence documents: describe the sequence in structured lines (points, modes, a decision table); the compiler writes the PPCL; sequences round-trip exactly between their text form and the model.
  • Block diagrams: 31 block types, an expression-first compiler, and cycle refusal in plain language.
  • Plain-English sequence-of-operations import: paste the SOO text and each item lands with a citation to the line it came from, and an honest list of what couldn't be resolved.
  • Vendor imports: block-diagram files and Desigo panel exports (.P2), each with a mapped / approximated / unmapped fidelity report. The .P2 importer is platform-first (D-123): real exports are decoded by the platform P2Parser, repaired and pinned against all 13 real held exports — 1,268 points, the module's counts equal to the platform's per file, point-name sets and program counts equal — with present values flowing through the decode (214 values, 125 of them carrying units). The older native grammar remains as a fallback for shapes the platform parser does not take, and the surface says so when the fallback is the one that decoded: its counts are checked against Desigo CC before they are trusted.
  • Siemens ABT job archives (.ABTArchive) open through an in-house 7-Zip subset reader: the archive is analysed from its member index alone, the import popup lists the detected content groups (Controllers & programs, Device parameters, Application types, Project information, Station, Balancer lists) for you to choose between, and only the checked groups import. Credential and key material is counted and classed from the index only — it carries no checkbox and is never imported. An archive outside the reader's subset (a solid archive, another compression coder, an encrypted archive) is refused honestly, by name.
  • Redact-for-sharing: strip a program for sending with the point-name mapping kept on your machine only.

Simulation & debugging

  • Compile-once simulation with exact priority arbitration, one implementation of statement semantics, so the editor, simulator, and debugger can never disagree about what a line does.
  • Plant models from components up to composed systems; a bench with 22 fault kinds, pass/fail checks, trends, run comparison, and saved JSON scenarios.
  • Time-scrub: every pass of a run is snapshotted; scrub back and inspect any point at any pass instead of re-running to the moment that mattered.
  • Debugger: line breakpoints, write-watchpoints, condition breakpoints, step in/over/out, run-to-cursor, a statement budget so a runaway loop stops instead of hanging, and coverage.
  • Declared approximations, in the open: the PID LOOP output is approximated (the vendor doesn't publish the form) and a small family of panel functions trace as no-ops in simulation. The bench says so rather than faking fidelity.

Library & data

  • File-based library: collections, auto-categories, tags, provenance and lint state recorded at save; archive export/import with collision policies.
  • Point database: CSV/JSON import with column aliases; unrecognised columns are reported, never guessed; unresolved references get U-marks in the editor gutter.
  • 21 settings, all real controls that drive the other panes, validated, never silently clamped.
  • An append-only error log in plain language: you see a message and a reference code, never a stack trace.

07 · Network+

The network workbench

Network+ opens on jobs, in plain language: find what's on this network, look at a device, why is this device offline, check this network's health, watch the traffic, prove this works, change something safely, talk to a device, what changed since last time. Pick the job, not the protocol.

  • Find. Ask the network who's out there. BACnet/IP discovery, Modbus, and OPC UA devices all land in the one shared inventory, you never re-type an address or a device number anywhere else in the app. The results land in one grid: the column headers and a per-column filter row stay in place while the rows scroll, the tick column and the Name block stay frozen at the left, and the grid is windowed — only the rows near the scroll position are drawn, however long the list is. Tick rows and the batch bar raises: back up the selection, save it, open its web interface, or report on it.
  • Report on this… Find (a completed run, or just the ticked rows), the device page, Health, the Test Bench, Records, and the backup surface all hand their subjects to Reports+: the studio opens with the subject as a source and its report preselected.
  • The device page is the spine. One page per device: its state, how it was found, its health axes, and every job for that device: points and values, schedules, trend history, its traffic, the console, its baseline. Protocols are capabilities of the device, never separate rooms to visit.
  • Watch. Packet capture that reads back in plain sentences (who asked, who answered, what changed) with a Capture completeness (interface drop counters) computed from the capture file's own counters, so you know what the capture can and cannot prove.
  • Health. A 40-check diagnostics catalog over your device records, your laptop's own readings, and a capture if you give it one. The score comes in three axes (Connected, Performing, Clean) and always arrives with the findings that moved it. An axis with no evidence says Not measured instead of guessing.
Front door, pick the job, not the protocol.

Test Bench: the only door that writes

Browsing surfaces never write, anywhere in Network+. Changes live here, as plans. Every plan is previewed from real reads first; the current values are backed up before anything is written, and if a backup read fails, the run blocks and nothing is written at all. One confirm, a graded run, verify by read-back, and a rollback that puts the old values back through the same engine.

A built-in Lab (a simulated peer with fault injection) lets you practise a plan against a device that misbehaves before a site visit depends on it. The Console is a real VT terminal for SSH, Telnet, and serial: SSH host keys are judged before any password is sent, and passwords live in session memory only, never stored.

Test Bench: preview → backup → confirm → run, stated on the surface; the simulated copy takes the rehearsal.
Network+ in full, workspace by workspace

Find

  • Discovery across BACnet/IP (its own BACnet stack, including BBMD foreign-device registration for reaching across subnets), Modbus, and OPC UA, plus an ARP / ping scan of what is answering on the wire.
  • Everything found lands in the shared Inventory Core as a DeviceRecord. Identity merges on BACnet instance + network first, then MAC, then IP, so re-finding a device updates its record instead of duplicating it.
  • Field changes are logged against the record; snapshots diff as ADDED / REMOVED / CHANGED.
  • The results grid: sticky column headers and filter row, the tick and Name columns frozen at the left, per-column filters that combine, sorting that never drops a selection, and windowing — only the rows near the scroll position are drawn, so a 10,000-device session set scrolls like a ten-device one.
  • The batch bar (with anything ticked): Back up selected, Report on selected… (the ticked devices become Reports+'s live device scope), Save selected list, Web interface, Clear selection. A completed run is reported separately, by Report on this run… beside the run summary.

Look (the device page)

  • Points & values in panel language with engineering units; schedules and calendars as the device reports them; trend history (graphs first, tables second, exportable with the report).
  • Per-device audit: out-of-service points, stale flags, held priorities: as sentences, in an attention list.
  • This laptop's own readings are evidence: Network+ keeps a record of this machine's own adapters and readings, so "the device dropped" can be told apart from "my laptop dropped".

Watch

  • Full BACnet decode under the plain-sentence layer: nothing is hidden, it's layered: sentence first, decode one step down, raw frame at the bottom.
  • Conversations view, filter presets, and a filter builder written in BAS terms instead of capture-filter syntax.
  • Capture completeness (interface drop counters): the capture's own counters state what fraction of the wire it actually saw: the badge travels with the capture.
  • Capture Compare between two captures; captures recorded on another BAS Hub import with their provenance noted; export as classic pcap.
  • BACnet/SC is reported honestly: Watch does not pretend to decrypt what it cannot.

Health

  • The full catalog: 40 checks in layers (this laptop, the network, the devices) including switch-port counters read over SNMP and a Wi-Fi section whose bounds are printed on its face; MS/TP bus checks that say plainly when a run holds no trunk evidence to judge.
  • Three-axis scoring (Connected / Performing / Clean) with a hard evidence rule: a check with no evidence reports Not run ("a pass would be a guess") never a silent pass.
  • "Why is this device offline?": the evidence run: name, ping, switch port table, and this laptop's local measurements, gathered in the open, landing on one verdict card.
  • Before/after compare against the previous run, and a report (Markdown) filed to a site with the run's evidence attached.

Test Bench (Prove / Change / Practise)

  • Plan sources: bounded templates in BAS words, classic rows, the device's own checklist, or record-a-real-action into a plan.
  • Every writing step is marked [WRITE] in the plan. Preview reads every current value first; the backup is a persisted file before the first write goes out; execution is sequential with a per-entry log; read-back verify where the plan asks for it.
  • Rollback writes the prior values back through the same engine and the same confirm discipline.
  • The full Modbus write set lives here only (the Modbus explorer elsewhere is read-only by design) preferring write-then-read in one transaction so the device's own read-back is the receipt.
  • Simulated devices: a simulated peer, clearly badged SIMULATED, with fault injection (a damper that sticks, a device that never reports COV, backup reads refused) so plans can be proven against a device that misbehaves.

Console (Talk)

  • A real VT terminal emulator: full-screen menus, colour, alternate screen, DEC line-drawing characters.
  • SSH, Telnet, and serial sessions prefilled from the device record, every default named on the surface. Host keys are judged before a password is ever sent; the profile type provably has no password field: passwords exist in session memory only.
  • Canned commands (the switch dialect most BAS gear speaks) plus your own, saved on this machine and offered on every session.
  • Send Break, honestly per wire: a real 250 ms pulse on serial, the IAC BRK byte sequence on Telnet, and a plain-word refusal on SSH, the surface says so instead of faking it.
  • Session logs in the PuTTY style, filed to a site.

Records

  • Revisit diffs in BAS words with identity-fallback matching, so a device whose address changed is still recognised as itself.
  • Baselines: save how a device should look; on the next visit, drift is reported per fact, and an unread point is never counted as changed.
  • A filed-records browser unifying captures, reports, checkout reports, and console logs, each with its SHA-256 fingerprint; hashed exports re-verify every file and name each VERIFIED / CHANGED / MISSING / unlisted.

09 · BAS Copilot (optional)

Help that stays on the machine

BAS Copilot is an optional module, chosen at install. It runs entirely on your computer: the panel says so on its face, and it's built so there's nothing to switch off, no account, no sign-in, no cloud, nothing typed into it leaves the machine.

  • It explains and drafts, a capture in plain words, an error translated, notes and reports drafted, questions answered about your records.
  • It never acts: no device writes, no sends, no file changes come from the assistant.
  • Skip it, and there is no chat surface anywhere, the icon simply isn't there.

At install, Setup checks your computer and offers only the model sizes it can run well. Locked tiers say why, in plain language.

Copilot details, tiers, swapping, and its privacy posture
  • How it runs: a local inference engine process started per conversation turn and stopped when the turn ends, no background service, nothing resident between questions. Chat history persists locally, on your machine, and the panel offers a one-tap delete.
  • Choosing and changing tiers: picked at install from the sizes your hardware supports (RAM is the gate; the reasons are shown, not hidden). You can change tier later in Settings → Modules; the new model downloads verified against its checksum, and a failed download changes nothing: the existing model stays byte-identical.
  • The download is the only network moment: the model file at install (or at a tier swap you start), verified against a published SHA-256 before it is used. Pre-staged model files placed beside the installer are picked up and hash-verified instead, the offline route for sites with no internet.
  • Zero-egress by construction: the module ships with no networking code of its own. What you type is processed on this computer and stays on this computer.
  • Honest limits: answer quality scales with tier, the smallest model is a helper, not an authority. Check its work the way you'd check a junior tech's.

Reports+, subject by subject

Reports+ is the reporting studio: vendor files and live subjects in, finished reports out — PDF, XLSX, CSV, TXT. Its catalog holds 59 report subjects, grouped by subject: Inventory, Programs, Files, Captures, Network, Commissioning, Live, Compare, Site. A report is offered only when the included sources can feed it; a report that cannot be built states the source it needs. Each report answers one question. This index explains every subject the same way the built-in help does: what it does, what feeds it — a file (and which types), an analysis, a live read, or a module surface's Report on this… door — and how it is configured.

Audiences, redaction, depth, sections, definitions

  • Audiences. Tech: full detail, trade terms, provenance complete. Boss: summary first — headline numbers and totals lead, the detail follows. Customer: a copy for release. Switching audience in the Preview rebuilds the report and carries its edits across. The audience column below is each subject's own set, as the catalog states it.
  • Redaction is a per-build choice, not an audience lock: on by default for Customer, off for Tech and Boss, flippable for any build. It covers IP addresses (masked to their first two octets), MAC addresses (masked out), account names, and network-identifying details. It never covers credential values, because credential values are never part of a report — parsers flag credential material by existence and role only. The cover states the choice either way, and every export's provenance prints it.
  • Depth is an option on the report you picked, never a separate report: Summary keeps the headline facts and exceptions; Detailed keeps every section; Mixed (the default) is summary first, with the detail behind it.
  • Sections. The point table, topology diagram, and charts can each be left out of the reports that build them, and any named section can be excluded at build time once the report has been built once in the session. Provenance is always included and cannot be left out.
  • Saved definitions. A configuration can be saved as a named definition for its report — depth, section toggles, filters, excluded sections — and applied in one pick. For a live report the definition also carries its live configuration. The definition store is written only when you save or delete, never as you browse.
  • Themes. Two print themes ship: BAS Hub Graphite and BAS Hub Light. The theme sets the printed palette only; it changes no content.
  • Every build also picks its audience, redaction, depth and sections, so the configuration column below names only what is specific to the subject: its audience set and any picks of its own.

13 · Updates

Updates happen when you say so

BAS Hub never checks for updates on its own. Settings → Check for updates is the only update path, and it's a button you press when you're online. Every download is verified by checksum and signature before anything is applied, and the previous version is kept until the new one has launched successfully once.

Update mechanics: how a release travels, step by step
  1. Check (only when you ask). The checker fetches the release manifest from the releases repository's latest release. Nothing is fetched in the background, ever; there is no schedule and no polling.
  2. Verify the manifest. The manifest is digitally signed (RSA) with the BAS Hub release key, whose public half is embedded in the app. A manifest that doesn't verify is refused outright.
  3. Plan. You see the new version, its notes, and exactly which modules would change, with sizes. Copilot items are separate and start unpicked.
  4. Download & verify again. Each file is checked against its SHA-256 from the signed manifest before anything is applied. A mismatch refuses the update.
  5. Apply, keeping the way back. The current version is set aside, not deleted. The new version must launch successfully once before the old one is let go; an update that fails to launch is reverted.
  6. IT control. An IT-policy switch can disable update checking entirely on managed machines, the Settings surface then says so, in words, instead of failing mysteriously.
Your data, maintenance, and uninstalling. Settings, logs and the activity log live in the suite's data folder, %LOCALAPPDATA%\BAS Hub\data. Device records do not live there: they live in the session working set while you work, and nothing is saved automatically — what you keep is what you file, into My Files & Library, the real folders on this computer, grouped by site under <site> / Exports /. Write-safety backups, captures and reports live where they are filed. Updates never touch any of it. Run Setup on a machine that already has BAS Hub and it opens as a maintenance screen instead: Update, Change modules, Verify, Uninstall. Uninstall removes exactly what the install receipt lists: the program, nothing else; your data is kept by default, and removing it too is an explicit choice, never the default. Exports never contain credentials.

14 · Trust, by design

Built like it has to earn its place on the laptop

◉

No telemetry. No phone-home.

Nothing is sent anywhere automatically, including crash reports. If BAS Hub ever crashes, it saves a structured report on your computer (the last 10 are kept, secrets kept out), and the next launch tells you in plain language that one was saved. Sending it anywhere is your act, never the app's.

⌂

Local-first data

One standard per-user folder; it survives updates and uninstalls; exports never contain credentials.

⬢

Secrets stay in the vault

Credentials are kept in Windows Credential Manager / DPAPI, never in plain-text files. Console passwords are held in session memory only and are never stored at all; console profiles by design have no password field.

◈

Write safety on live controllers

The Test Bench is the only door that writes. Preview from real reads → backup persisted first → your confirm → graded writes with read-back verify → a receipt, and rollback through the same path. A failed backup read stops the run cold: nothing is written. Browsing surfaces hold no write code path at all.

✓

Verified downloads

Release manifests are digitally signed and payloads are checksummed; a download that doesn't verify is refused, not installed. The installer itself verifies the payload hash before it stages a single file.

☰

Least privilege, nothing lurking

Per-user install, no administrator rights for the app, no background services installed, no listening sockets opened by default. Anything that listens runs only while you run it, shows its state, and stops when you stop it.

Honest surfaces. Where the app can't do something (a capture that proves less than it seems, a health axis with no evidence, a break a wire doesn't support) the surface says so, in words, on its face. That posture is a feature, and it is tested like one.

15 · FAQ

Questions, answered straight

Is BAS Hub open source?

No. BAS Hub is proprietary software, distributed as binaries. The releases repository is the releases and information point; it does not and will not contain source code.

Does it work on a site with no internet?

Yes: it was designed for exactly that. Field networks are often offline, so everything works locally; the only features that want a connection are the ones you start yourself (an update check, a Copilot model download: which can also be pre-staged beside the installer and hash-verified offline).

Do I need administrator rights to install or run it?

No. The one exception is the optional Npcap packet-capture driver, which installs through its own signed installer and asks for approval then. Everything else in BAS Hub works without it, and without admin rights at all.

Is Copilot a cloud AI? Does it send my data anywhere?

No, and no. Copilot is an optional module that runs a model entirely on your computer; it ships with no networking code. If you don't install it, BAS Hub has no chat or AI surface anywhere.

Can Copilot change anything on a device?

No. Copilot explains and drafts, it never acts. It has no path to device writes, sends, or file changes. Every write in BAS Hub goes through the Test Bench's confirm path, by a person.

How good are Copilot's answers?

It depends on the tier, bigger models reason better, and Setup only offers tiers your machine can run well. Treat it as a capable assistant, not an authority: check its work the way you'd check a junior tech's.

Where does my data live? What happens when I uninstall?

Everything lives in %LOCALAPPDATA%\BAS Hub\data. Uninstalling removes the program and leaves your records in place; they reconnect if you reinstall. Deleting the data too is an explicit opt-in, never the default.

Can IT deploy it silently?

Yes. Silent per-user deployment with module and Copilot selection, verification and uninstall verbs, and documented exit codes (full table in the Download section above and in the installer's own --help text). An SBOM ships with every release, and an IT-policy switch can disable update checking on managed machines.

Does Programmer+ download programs to panels?

No. Programmer+ is an authoring workbench: it works on program files (editing, checking, simulation, imports). It never communicates with a panel.

What does Reports+ report on?

59 report subjects, fed two ways. Files you add in the studio: Tridium station backups (.dist) and wiresheets (.bog), Siemens panel exports (.P2) and ABT projects (a folder tree, or an .ABTArchive opened through its analyse, choose, import popup), Distech GFX projects (.gfx) and ECLYPSE controller backups (.ecybackup), packet captures, discovery exports, health run files, and PPCL program files. Live and module-fed subjects, handed over with Report on this…: a Find run or its selected rows, a device page and its watch session, a Health run or offline verdict, a Test Bench run, Records, a device backup — and from Programmer+, a program or session set, a Simulator bench run or debug session, a conversion, the code library, and the loaded point database. A family of Live reports needs no file at all: it reads the devices you picked, live, when you build. The full index of the 59, each explained, is in the help section above.

Who is a report for, and what does redaction do?

Every report is built for one of three audiences: Tech (full detail, trade terms, provenance complete), Boss (summary first; headline numbers and totals lead), or Customer (a copy for release). Some reports are Tech-only or Tech-and-Boss by their subject — station account names, for one, are site security data and have no Customer copy. Redaction is a per-build choice, on by default for the Customer audience and flippable for any build: IP addresses are masked to their first two octets, MAC addresses are masked out, and account names and network-identifying details are covered. Credential values are never part of a report in the first place — parsers flag credential material by existence and role only. The cover states the redaction choice either way, and every export's provenance prints it.

What formats do reports come out in?

PDF, XLSX, CSV, and TXT — the preview and every export render the same built report, section for section. Depth (Summary, Detailed, or Mixed), the sections included, typed filters, and the print theme (BAS Hub Graphite or BAS Hub Light) are build-time choices, and a configuration can be saved as a named definition for its report and applied in one pick. In the Preview you edit the built report itself — title, sections, your own added text, and, under a per-report unlock, individual sourced values — before it exports; an export can also be filed into the Library in the same step, under the site you name.

What does "0.9.0" mean: is this finished software?

The version number means what it says. 0.9.x is the pre-1.0 line. The current release is 0.9.4, the first release published as stable: it is the public download, and because it is a stable release the app’s update check (which reads the latest stable release) offers it to an installed 0.9.3 or 0.9.2. The stable label does not retire the reservation: 1.0.0 is reserved for the first release proven end-to-end in the field. 0.9.3 was an internal staged build, superseded by 0.9.4 before publish and never publicly released. 0.9.2 is a legacy build, unsupported, kept for reference and rollback; 0.9.0 and 0.9.1 are internal builds, not public releases. Every version ships with its own release notes, and this site is updated with every release: a site that no longer matches the shipped build is treated as a defect, same as stale help. See Versions for each release’s summary.

16 · Support

Report it where it can be acted on

Bugs and feedback land as issues on the releases repository: in the open, where their state is visible. There is no ticket system and no support inbox; these two forms build the issue for you and hand it to GitHub with everything filled in. Review it there, then submit.

Report a bug

Something BAS Hub did wrong, on a machine, in the field. Say what happened, in order.

Attach the failure log. BAS Hub writes a log file for every failure, at the moment it happens. Settings → Open logs folder takes you to it. Attach that file to the issue on GitHub: it carries the full diagnostics and is the single most useful thing you can send. Issues are public: leave out site data, addresses, and credentials.

Send feedback

An idea, a request, or a general impression of the tool as it stands. All of it is read.

Feedback is filed as a public issue labelled as feedback, so its outcome is visible too. Say what the field work needs; feature claims on this site are only ever made for what has shipped, and good requests are how the next release earns them.

What happens next. Every report is reviewed and checked against the product as shipped, reproduced, or the issue says plainly that it could not be. Each report is answered on its own issue, in the open. Fixes ship in releases, and the reporter-visible outcome lands in that release’s patch notes (and on this site’s Versions page). Support is best-effort by the maintainer: no response-time promise is made, and none should be inferred: what is promised is that nothing disappears into a private inbox.
